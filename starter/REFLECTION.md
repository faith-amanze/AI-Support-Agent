# Reflection

**Design decision:** I chose to separate the agent's custom cross-session memory (MemoryHook, backed by CustomerSupportMemory) from any of AgentCore's own built-in memory features, rather than relying solely on the toolkit's automatic short-term memory. This gave me explicit control over what gets retrieved and saved on each turn -- semantic facts and user preferences keyed by customer namespace -- which proved essential for grounding responses like recalling a customer's loyalty tier and points balance across sessions with concrete numbers rather than vague summaries.

**Challenge encountered:** The most significant challenge was navigating a sandbox AWS account with deliberately restricted IAM permissions. Creating a self-managed Knowledge Base failed because the execution role lacked aoss:CreateSecurityPolicy for OpenSearch Serverless; deploying via CodeBuild failed silently with no diagnosable error because CloudTrail lookup was also denied; and even after deployment succeeded, the Browser Tool failed with bedrock-agentcore:StartBrowserSession denied on the runtime execution role. I worked around the first two by switching to a Bedrock-managed Knowledge Base (avoiding OpenSearch Serverless entirely) and a local Docker build path instead of CodeBuild. The Browser Tool restriction, however, was a genuine dead end -- the execution role simply lacks that permission with no self-service path to grant it, which I've documented as a confirmed, unfixable sandbox limitation rather than a code defect.

**Production consideration:** This project underscored how tightly scoped IAM permissions need to be between AgentCore components that seem logically connected but require explicit, separate grants -- for example, creating a Knowledge Base does not automatically grant the agent's runtime execution role permission to call bedrock:Retrieve against it; that required a manual inline policy. In a production deployment, I'd formalize this as an infrastructure-as-code template (e.g., CloudFormation or CDK) that provisions all cross-service permissions atomically, rather than discovering missing grants reactively through runtime AccessDeniedException errors during testing.
