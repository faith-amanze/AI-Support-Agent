# Reflection

**Design decision:** I chose to separate the agent's custom cross-session memory (MemoryHook, backed by CustomerSupportMemory) from any of AgentCore's own built-in memory features, rather than relying solely on the toolkit's automatic short-term memory. This gave me explicit control over what gets retrieved and saved on each turn -- semantic facts and user preferences keyed by customer namespace -- which proved essential for grounding responses like recalling a customer's loyalty tier and points balance across sessions with concrete numbers rather than vague summaries.

**Challenge encountered:** The most significant challenge was navigating a sandbox AWS account with deliberately restricted IAM permissions, and learning to distinguish which restrictions were genuinely fixed versus which could be resolved with targeted permission grants. Some restrictions proved to be hard account-level limits with no workaround: creating a self-managed Knowledge Base failed because the execution role lacked aoss:CreateSecurityPolicy for OpenSearch Serverless, and deploying via CodeBuild failed silently because CloudTrail lookup was also denied, blocking root-cause diagnosis through normal means. I worked around both by switching to a Bedrock-managed Knowledge Base (avoiding OpenSearch Serverless entirely) and a local Docker build path instead of CodeBuild. Other restrictions, however, turned out to be missing grants rather than hard blocks: the agent's runtime execution role lacked bedrock:Retrieve on the Knowledge Base and bedrock-agentcore:StartBrowserSession for the Browser Tool, both of which I resolved by attaching targeted inline IAM policies directly to the execution role. This distinction -- between account-level resource-creation restrictions and simply missing cross-service permission grants -- was the key insight that let me systematically resolve every blocker except the two genuinely locked-down provisioning actions.

**Production consideration:** This project underscored how tightly scoped IAM permissions need to be between AgentCore components that seem logically connected but require explicit, separate grants -- for example, creating a Knowledge Base does not automatically grant the agent's runtime execution role permission to call bedrock:Retrieve against it, nor does deploying an agent with a Browser Tool automatically grant bedrock-agentcore:StartBrowserSession. In a production deployment, I'd formalize these as an infrastructure-as-code template (e.g., CloudFormation or CDK) that provisions all cross-service permissions atomically at deploy time, rather than discovering missing grants reactively through runtime AccessDeniedException errors during testing.
